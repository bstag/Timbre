# B20 feature findings and remaining controls

This file preserves dated investigation results. Consult [current validation status](../validation/status.md) for subsequent results and remaining limits. Referenced `artifacts/` and `preservation/` files are local evidence excluded from source checkouts and ZIPs.

Investigated on 2026-10-05 against the installed Gaming Suite 1.12.2.1185, captured B20 driver topology, our source/tests, and EPOS's B20 user guide.

## What we found beyond the percentage controls

The clearest extra capability is **a separate hardware sidetone mute**. The B20's monitoring branch has its own mute and stereo volume controls. Our app exposes that mute, and the user confirmed both level adjustment and mute by listening. Suite's captured 0% position set both monitoring channels to -31 dB with the monitoring branch still unmuted. Consequently, the captured slider's 0% action and our independent monitoring mute are different operations. This does not establish that every Suite version lacks a separate mute elsewhere in its interface. We have not completed that UI inventory. [Sidetone investigation](b20-sidetone.md), [0% topology fixture](../../tests/Timbre.Tests/Fixtures/b20-topology-sidetone0.json), [hardware report](../../artifacts/sidetone-verification-009f.json).

| Finding | Evidence classification | Relation to Gaming Suite |
| --- | --- | --- |
| Independent sidetone mute | Confirmed hardware control; live readback/isolation and user listening passed | Additional explicit control in our app compared with the captured percentage-slider operation; absence from all original UI paths is unproven |
| Native sidetone dB and range | Driver reports -34.5 to +9 dB, nominal 1.5 dB step; captured values have finer resolution | Our app exposes native dB rather than Suite's nonlinear percentage conversion; the reported minimum is lower than the captured 0% value of -31 dB |
| Separate left/right sidetone values | Confirmed two-channel descriptor and backend support; asymmetric behavior tested offline | Potential balance control; normal app slider changes both channels equally. Independent asymmetric hardware writes/listening have not been validated, and original UI exposure is unknown |
| Combined control profiles | Implemented and tested in our app | Save/restore microphone Windows level/mute, mapped processing flags/values/EQ, and sidetone together. This is app functionality rather than newly discovered hardware. Exact equivalence to Suite's preset coverage has not been established |

The sidetone adapter permits the driver's reported -34.5 dB minimum, but we have not listening-tested that endpoint. Suite's initial captured maximum was +9.0859375 dB; our code preserves that compatible legacy value for restoration and normally uses +9 dB as the slider maximum. These levels are hardware control units, not calibrated acoustic gain measurements. [Sidetone range and conversion evidence](b20-sidetone.md), [native adapter](../../src/Timbre.Core/WindowsSidetone.cs), [state/range guards](../../src/Timbre.Core/Sidetone.cs).

The backend retains left and right values separately, calls `SetLevelAllChannels` with two supplied values, and preserves existing channel differences for mute-only operations. The current UI deliberately provides one level slider. Offline tests cover asymmetric preservation and partial writes; the live hardware test changed both channels together. A balance UI should follow a reversible asymmetric hardware and headphone listening test. [Backend](../../src/Timbre.Core/WindowsSidetone.cs), [UI](../../src/Timbre.App/MainWindow.xaml.cs), [regressions](../../tests/Timbre.Tests/SidetoneTests.cs), [live test](../../tests/Timbre.Tests/HardwareSidetoneTests.cs).

Profiles are tied to a physical device identity and endpoint direction. Profile application validates adapters before changes and attempts restoration after failure while preserving detectable newer edits. A microphone profile does not also include the separate playback endpoint's volume. The format is our own JSON, not Suite's preset format. [Profile implementation](../../src/Timbre.Core/Profiles.cs), [current control behavior](../development/microphone-protocol-and-tests.md).

## Existing features, not hidden discoveries

EPOS's user guide describes hardware gain, listening volume, microphone mute, four pickup patterns, and their Suite displays; it also documents Suite noise cancellation, sidetone, and microphone EQ. Pickup pattern is selected with the physical switch and displayed in Suite. Our app now has an experimental status display, with a live cardioid capture and tested decoder. Native requests remain unreliable, so this display is not yet a completed hardware feature. [Pickup-pattern investigation](b20-pickup-pattern.md), [B20 user guide, pages 12–18](https://www.eposaudio.com/globalassets/__pim/products/b20-series/b20---grey/1e8d40d5-3106-4a4a-b0eb-9265a2ceb6aa_26740_b20_userguide_a02_0122_en_int_original.pdf).

Noise gate, filter level, high-pass, and Warm/Clear/Custom voice EQ were mapped through the user's Suite changes and static inspection. They are recovered existing controls. Our separate enable switches preserve saved levels/curves when disabled. We have not established that those switches are unique to our UI. [Golden captures and field mapping](../development/microphone-protocol-and-tests.md), [fixture inventory](../../tests/Timbre.Tests/Fixtures/README.md).

Microphone meters and voice-monitor telemetry appear in the vendor's managed interface metadata (`micMetersEnabled`, `enableVoiceActivityMonitor`, `enableVoicePeakMonitor`, and corresponding event/parameter methods). Those names alone do not prove a new DSP feature, B20 support for every monitor, or absence from the original UI. A meter added to our app would be useful feedback, but should not be presented as an unlocked B20 hardware feature. [Metadata](../../artifacts/ui-metadata.json), [event/parameter methods](../../artifacts/pipe-methods.json).

## Candidates that remain unvalidated

Read-only string inspection of the installed `C:\Windows\System32\EAPO.dll` found the UTF-16 strings `mic_speech_compressor_enabled` and `mic_speech_compressor_preset`, plus an ASCII compressor buffer error. The inspected image's recorded SHA256 is `F83F40E12FA2683A8C625863D3A459D92BDD30549E7DA74AC43EED84751388CA`. These are **implementation clues**, not proof that a working user-selectable B20 compressor exists. We have not mapped its ranges or writes, measured compression, or established whether Suite uses it indirectly. [Binary identity and existing investigation](../development/microphone-protocol-and-tests.md).

Managed `ApoParams` metadata exposes `micFrcEnabled`, `micFrcPreset`, and `enableAutomaticGainAdjustment`. Later static inspection of `MicrophonePageView.ShowMicDirectionButton` found that displaying a pattern also sets `micFrcEnabled = 1` and `micFrcPreset = directionValue`. This links FRC to pattern-dependent processing; its algorithm remains unestablished and it must not be called a hidden compressor. Automatic-gain metadata likewise does not establish a supported B20 AGC control. The recovered native `getMicDirection` request and live cardioid input report support status reading, without proving software can override the physical switch. We leave these unowned processing fields untouched. [Pickup-pattern evidence](b20-pickup-pattern.md), [metadata](../../artifacts/ui-metadata.json), [managed UI IL](../../artifacts/b20-pattern-ui-il.json).

No working hidden compressor, AGC, remotely selectable pickup pattern, or B20 surround feature has been validated. Capturing unrelated fields or finding a name in shared vendor code is insufficient to claim a supported control.

## What to do next for the B20

The basic listening and frequency-label gaps are now resolved: on 2026-10-05 the user confirmed that noise filtering and high-pass work and EQ presets make an audible difference. Their Suite screenshot supplies the nine labels **64, 125, 250, 500 Hz, 1, 2, 4, 8 and 16 kHz**, now shown in our app. Gate already passed its WASAPI diagnostic and sidetone has user listening confirmation. These are listening results and vendor UI labels, not calibrated per-band measurements. [Validation and screenshot evidence](../development/microphone-protocol-and-tests.md).

1. **Finish reliable pickup-pattern readout:** the query, cardioid report, four enum values, identity guards and display are implemented. Requests remain intermittent, including a timeout with service/UI stopped. Validate reliable reads and all four physical-switch positions before marking the control ready. This restores an original Suite display; there is no pattern setter.
2. **Check lifecycle:** the administrator service-stop experiment showed that processing's control interface disappears while hardware sidetone still works. Service/UI restart eventually restored all mapped settings exactly. Keep the service for now, then plan physical reconnect and reboot/profile checks when someone can access the device. Results feed the [installer and dependencies plan](../roadmap/installer-and-dependencies.md).
3. **Only then consider optional additions:** independently verified sidetone balance, deeper audio measurements or compressor investigation can follow the core work. They do not block a usable B20 control replacement.

The original investigation changed no device settings and executed no vendor binaries. Primary EPOS PDF text was available; its screenshot fetch failed, so claims about original UI absence remain explicitly limited. The later user-provided screenshot confirms the EQ frequency labels only; it does not establish absence of other controls elsewhere in Suite.
