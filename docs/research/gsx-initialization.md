# GSX 300 processing initialization

Implemented 2026-10-08 as a bounded console experiment. Actual fresh GSX creation, service-stopped microphone/playback control transactions and exact recovery passed on hardware after a controlled Windows Audio restart. The installed EPOS driver and Windows-hosted audio processor remain required. Audible DSP after fresh creation, cold boot, managed GSX reconnect and automatic GSX restoration remain unvalidated. This is not an installed service.

## Shared state and safeguards

GSX microphone and playback processing use the same model-specific object set:

`Global\CF4B411F-BE2B-4D84-8106-EC27CA0F8F05_1395_0098_{mutex,memory,event}`

B20 uses the separate `009f` set. GSX startup therefore accepts both complete microphone and playback settings in one explicit diagnostic input. The input is bound to the physical USB instance, not endpoint GUIDs or friendly names. Both active endpoints must be present, belong to that instance and be unambiguous among connected GSX units.

The helper validates the snapshot before opening native objects: schema, complete gate/filter/switch/microphone EQ, complete surround/playback EQ/reverb, compatible header/layout and agreement between typed settings and captured bytes. Unknown nonzero data beyond the recovered 2112-byte logical structure is refused rather than silently discarded. The 4096-byte mapped view and common native creation mechanism reuse the tested B20 implementation; the GSX experiment replays its own validated current capture rather than assuming B20 settings or seed-free defaults are suitable for GSX.

`--initialize-gsx` requires the vendor service to be stopped and holds a separate GSX initializer ownership lock. Existing complete objects, partial sets and creation races are refused without overwriting existing memory. New objects receive the captured GSX configuration and notify the processor. Health checks validate both pages and both connected endpoint identities. There is no repeated settings replay, reconnect policy, profile store mutation, driver installation, HID write or VST routing. GSX high-pass remains unsupported as an editable control; its captured state is preserved. Windows level/mute and USB sidetone are not part of the initialization snapshot and are not changed.

`--validate-gsx` validates the snapshot and physical endpoint pair without opening or creating vendor objects. Its `validated.json` explicitly reports no settings writes and no object creation; it never produces a fresh-initialization readiness claim.

## Hardware pilot

Read-only preparation, with the vendor service running:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '.\tools\Test-GsxInitialization.ps1'
```

Temporary service-stop test, in administrator PowerShell:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '.\tools\Test-GsxInitialization.ps1' -StopSuiteTemporarily
```

Leave Gaming Suite idle. The runner captures current settings and full buffers and validates its device-matched startup file. If B20 is present, a read-only retention helper keeps its existing objects alive while the vendor service is stopped. The runner closes/restores the original Suite UI, stops/restarts the service, requires `CreatedFresh=true` for GSX, runs microphone and playback control/restoration checks and compares both complete buffers. It restarts vendor support while helpers still hold the objects, then stops its own helpers and compares all diagnostic controls with baseline. Settings stores and service startup policy are unchanged. Restoration failures remain failures even when initialization was safely refused.

Reports go to a fresh `artifacts/gsx-initialization/<UTC timestamp>-<id>` directory. `summary.json` distinguishes read-only preparation, actual fresh initialization, control readback, optional audio, settings restoration and service recovery. A `BlockedByExistingObjects` result means a warm audio process still holds the GSX set; it is not an initialization pass. The runner restores service/UI and exits 3. A physical disconnect/reconnect is a separate next step, rather than resetting active memory or force-closing unrelated audio applications.

The first pilot does not require listening, unplugging or reboot. When old GSX objects remain retained, the optional physical-reconnect experiment is:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '.\tools\Test-GsxInitialization.ps1' -StopSuiteTemporarily -ReconnectGsx
```

Wait for the runner's unplug instruction, disconnect only GSX and wait for its observed-removal message before reconnecting. Both steps have sixty-second limits; timeout/error restores vendor support. The runner observes both endpoints disappearing and returning as the same physical GSX before attempting fresh initialization. It does not unplug/replug devices itself or implement managed helper reconnection. Leave B20 connected and avoid editing controls during the test.

Add `-HardwareAudio` only with steady adequate GSX microphone input; it captures numerical metrics, saves no recording and keeps the existing signal-quality/attenuation criteria. Inconclusive audio exits 2, separately from successful initialization/control/restoration. Cold boot and automatic restore remain untested; physical discovery during the optional experiment is distinct from managed helper reconnect recovery.

## Controlled audio-engine boundary

The current preparation sequence passes **511 regression checks**. A new failing regression reproduced the exact `Sequence contains no matching element` symptom when endpoint metadata became empty after preparation; the corrected implementation passes it and the USB removal/replacement/multiple-unit, invalid preparation and resumed-live-validation cases. Red and final evidence: `artifacts/gsx-prepared-discovery-red-20261008.{json,log}` and `artifacts/gsx-prepared-discovery-tests-20261008.{json,xml,log}`. Host and test builds have zero warnings/errors, and the Windows PowerShell 5.1 runner parses successfully.

Actual read-only preparation, cancellation and explicit-request refusal with services Running passed on this PC: `artifacts/gsx-initialization/20261008-124506-590c4257/prepared-host-check`. The prepared report identifies the live GSX pair and its sole present physical USB root; cancellation exited successfully, and a separate request with vendor support Running failed before native creation and produced no readiness. Independent diagnostics found all controls unchanged, both full 4096-byte GSX/B20 buffers identical to baseline and no remaining helpers (`prepared-host-assessment.json` in that run). `tools/Test-GsxPreparedHost.ps1` makes those preparation/guard checks repeatable from a fresh current startup snapshot, without stopping services. These are preparation and refusal checks, not a fresh-initialization pass.

The first audio-engine restart pilot (`20261008-120835-0065c329`) failed before fresh creation: active-only discovery could not find the GSX pair with Windows Audio stopped. Both services recovered, but the B20 Windows microphone gain reset from -7.5 dB to -24 dB. Its processing configuration and all other controls remained intact. A subsequent guarded restoration wrote only the B20 gain, verified -7.5 dB, and an independent diagnostic found zero differences across all captured controls, both services Running and no helper processes. Evidence: `audio-recovery-result.json`, `after-gain-restoration.json` and `after-gain-restoration-assessment.json` in that run. The original failed result remains unchanged.

The first correction attempted all-state, metadata-only discovery after the audio stop. Its administrator pilot (`20261008-123234-b2e71ec8`) still failed before creation: the saved `initialize/startup-discovery.json` contains no usable endpoint pair. This filtered capture does not distinguish absence of raw Windows endpoints from failure of their PnP ancestry lookup. Both services returned to Running, Windows gain/mute recovery succeeded, and the final and independent diagnostics found zero control differences. Evidence: `summary.json`, `audio-engine-recovery-levels-restored.json` and `independent-recovery-assessment.json`. That failed initialization result is preserved.

The revised `--initialize-gsx-paused` sequence prepares a live-validated microphone/output pair while Windows Audio is running, before either service stops. Preparation validates the explicit snapshot, exact endpoint IDs, current USB identity and a unique present physical GSX. It reports `prepared.json`, opens no vendor effects objects and waits for an explicit request containing its process ID and physical device instance. Cancellation or timeout before the request produces no fresh readiness. The runner then stops vendor support and Windows Audio and requests initialization from the already prepared process. Native creation still requires both services Stopped and refuses existing/partial objects or creation races.

During the audio pause, discovery uses only the pair validated in this process and a fresh `CM_Get_Device_ID_ListW` present-USB query. It does not ask the unavailable audio endpoint service to rediscover the pair. USB removal, replacement or another physical GSX causes refusal; interface child nodes and case aliases do not count as extra physical devices. The PnP query has a bounded buffer and retry count and does not generate service devnodes. Normal app discovery is unchanged. When audio resumes, the helper returns to active endpoint validation and continues checking current physical USB uniqueness. Readiness and heartbeat evidence report `DiscoveryMethod` and physical GSX instances. This revised sequence passed the administrator fresh-creation/control pilot recorded above; audible processing after fresh creation remains unvalidated.

The runner now restores captured Windows level/mute values after the audio restart, including the failure path. It waits for previously readable audio endpoints, validates every physical identity and expected current value before its first write, rechecks immediately before each write, skips unchanged values, and verifies restored level/mute/dB. Edits after its expected-state capture cause refusal rather than overwriting the edit. This is a bounded test restoration policy, not app auto-restore; leave other controllers idle during the experiment. The read-only B20 lease can stay held while audio endpoints are temporarily inactive only if Windows Audio is stopped and the original physical B20 remains present. Ordinary B20 removal remains a failure for this retention mode.

Regression evidence: `artifacts/gsx-paused-audio-tests-20261008.{json,xml,log}`. Five recovery cases cover reset gain, unchanged devices, stale expected state, concurrent edits and missing/ambiguous identities; three additional GSX cases cover pinned metadata selection and rejection paths. `tools/Test-ApoRecoveryChecks.ps1` also passes three Windows-audio readiness cases in addition to its eighteen processing/reconnect cases.

When a brief interruption of all Windows audio is acceptable, the separate administrator experiment is:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '.\tools\Test-GsxInitialization.ps1' -StopSuiteTemporarily -RestartAudioEngine
```

Windows Audio (`Audiosrv`) must initially be Running with no running dependent services. The runner keeps B20's existing configuration held, stops the EPOS service and Windows Audio, uses the already live-prepared endpoint pair and current physical PnP presence for GSX creation before restarting audio. It refuses retained/partial objects as usual. On success, the GSX helper holds the new seed-matched configuration while Windows Audio restarts; microphone/playback control tests follow with vendor support still stopped. Failure and success paths restore Windows Audio before EPOS support, release only our helpers and compare both devices. It does not stop Audio Endpoint Builder, kill audio-engine processes, alter driver bindings or change service startup types. No physical reconnect is combined with this mode. This controlled boundary is not a cold-boot test.
