# EPOS Control: implementation and extension guide

Current behavior is summarized in [validation status](../validation/status.md). Dated UI milestones below retain their original evidence and test counts.

## Working release

The native 64-bit Windows WPF app discovers EPOS/Sennheiser USB audio endpoints using Core Audio and walks the Windows device tree to identify the physical USB ancestor. It controls endpoint level and mute without EPOS Gaming Suite. Microphone and playback are separate selections. The Elgato virtual endpoint with an EPOS name is excluded by its actual ancestry.

The app applies user control edits live by default, with a 150 ms quiet interval capped at 300 ms during long drags. Unchecking Apply changes live restores manual Apply buttons. Readings and connection discovery update every two seconds; startup reads and endpoint selection never enqueue edits. B20 processing can optionally restore on startup or an observed reconnect after explicit opt-in. Named profiles live in `%LOCALAPPDATA%\EPOS-Control\profiles.json`, with first-run import from the previous executable-directory `data/live/profiles.json`. Processing restore state remains under `%LOCALAPPDATA%\EPOS-Control\processing-state`; demo/verification data is separate.

The GSP 301 is an analog headset. When connected to the GSX 300, it uses the GSX 300 playback and microphone endpoints; it does not require a separate USB adapter implementation in this app.

The default layout shows endpoint volume/mute and, on GSX output, sound mode. The microphone studio opens with its main controls and a combined activity/EQ plot; EQ adjustment sliders, profiles and feature details are expandable sections. Sound/Microphone buttons navigate within the selected physical USB instance. Discard edits cancels queued work and reloads readings. Apply buttons are hidden during live mode. Named profiles are explicitly saved or loaded; Save to selected updates the chosen device/page profile. A live save flushes queued edits first and aborts on apply failure; manual-mode drafts are excluded. Setup profiles are a separate collapsed section above device navigation and save selected pages together. They capture inline snapshots rather than references to mutable device profiles. See [profiles and live controls](../user-guide/profiles-and-live-controls.md).

`SetupProfileController` coordinates read-only capture, identity resolution, preflight and explicit multi-page application through existing backend interfaces. Saves capture checked connected pages and can explicitly retain checked disconnected snapshots from the selected setup. Unchecked pages are omitted, including when updating the selected setup. Missing members are skipped on apply. Unavailable checked adapters and ambiguous identities fail preflight before writes. It rechecks each page's observed state before applying; a failure stops further pages and returns explicit partial results without claiming atomicity across devices. `SetupProfileStore` validates versioned snapshots, enforces unique names and members, uses bounded locks and atomic writes, and guards selected updates against concurrent changes. Setups live in `%LOCALAPPDATA%\EPOS-Control\setups.json`. Applying one never changes Windows defaults or queues reconnect restoration; successful B20 processing follows the existing restore-state persistence policy.

Device-page inclusion and the setup checklist share observable choice objects. New setups include nothing implicitly; choosing a saved setup restores its membership. Checkbox edits do not change hardware and must be saved before applying a preset with changed membership. Optional Select edited pages uses successfully applied direct adjustments from this app session, with live edits flushed first. Reads, unapplied/failed drafts, profile/setup loads and automatic restores are excluded from that history. It selects pages only; complete page snapshots are still saved on explicit action. Empty membership is rejected and does not overwrite a saved setup.

Setup membership is displayed in physical-device groups. Parent checkboxes select or clear all listed child pages; partial selections preserve independent Sound/Microphone scope. Grouping removes the direction suffix only from canonical USB identities, retaining vendor/product/physical instance. Canonical disconnected pages can join a connected sibling; unverified legacy identities remain separate. This is a UI selection shortcut over existing endpoint snapshots, with no profile schema change or automatic inclusion of future pages.

## Modules and adapters

- `IAudioBackend` is the interface shared by the Windows Core Audio adapter and the functioning demo adapter. It provides discover/read/apply operations. Native COM pointers, device-tree traversal, mix-format queries, disconnection checks and restoration on failed writes remain in the Windows implementation.
- `DeviceCatalog` uses the USB identity and `devices.json` to describe known model-specific features. Basic Windows controls work on other discovered EPOS USB models. Unknown models do not inherit another model's sidetone/surround commands.
- `ProfileStore` validates complete persisted values and binds new profiles to USB vendor/model/instance plus audio direction, independent of friendly names and endpoint GUIDs. Legacy strict identities remain compatible and upgrade on explicit save. It imports only into an absent destination, atomically writes under a bounded file lock and compares selected saved records before updating them. Profiles are never loaded automatically by selection or startup.
- `LiveApplyQueue` combines control-section edits and binds queued work to an endpoint incarnation. The UI cancels it before selection, discard or explicit restoration, reads without enqueueing, applies through existing adapters, and never automatically retries failed work. Named profile persistence remains separate from auditioning.
- `IMicrophonePacketSource` separates shared-mode WASAPI capture from `MicrophoneSpectrum` analysis. `MicrophoneMonitor` owns the capture thread and publishes immutable RMS/peak and nine-band summaries. The optional WPF activity view keeps measured dBFS separate from EQ settings in dB and labels the recovered gate geometry as a visual guide. Collapse, device selection and shutdown stop capture; analysis never changes profiles or hardware controls. See [live microphone view](../user-guide/live-microphone-view.md).
- `ProcessingStateStore` persists complete, verified B20 processing after successful Apply, separate from profiles and opaque initialization snapshots. It has strict schema/device validation, atomic per-device files and bounded exclusive file locks. `ProcessingRestoreSession` applies explicit opt-in once per observed connection; default polling never writes or replaces remembered settings. Hardware success and persistence failure have separate outcomes. See [processing state and tests](../user-guide/processing-state.md).
- `B20HostLifecycle` coordinates the explicit physical target, input validation, opt-in restore, once-per-connection policy, handle release and bounded retries. `WindowsB20HostConnection` owns native attachment/fresh creation and service-before-write guards. `B20HostOwner` excludes competing initializers/managed helpers; read-only retention remains independent. See [managed helper lifecycle](../research/b20-host-lifecycle.md).
- `SuiteApoRequest` prepares a surround update from a supplied current request snapshot and also returns its restoration bytes. It verifies one device, keeps other effect parameters intact, and refuses an unknown starting surround state. It does not open named pipes or send bytes. Test fixtures are synthetic and do not establish live service compatibility.
- `IPlaybackEffectsBackend` supplies GSX playback read/compare/apply with native and demo adapters. `ApoPlaybackCodec` owns only the validated surround byte and nine playback EQ floats. Native sessions enforce separate microphone and playback write whitelists. The app never creates GSX processing objects; it uses the existing installed processor interface. Profiles include playback processing, while older profiles leave it unchanged. See [GSX control evidence and tests](../research/gsx-playback-controls.md).

The GSX microphone adapter now uses the existing `_1395_0098` objects with endpoint-aware preflight and native patch validation. Gate/filter/EQ and their enable bits are writable; high-pass at 71 is rejected and preserved. B20 uses `_1395_009f` and retains its own high-pass/sidetone controls and host lifecycle. Device/setup profile preflight rejects unsupported GSX changes before any endpoint writes. Both microphone pages share the combined graph. The GSX Sound studio reuses analysis with a shared-mode loopback source; capture is opt-in and stops on selection/shutdown. See [GSX microphone evidence](../research/gsx-microphone-controls.md) and [playback view](../user-guide/live-playback-view.md). The 2026-10-08 source readiness run passed 511 regressions, 121 WPF scenarios, and 9 offline GSX probe guards. Earlier counts below describe historical UI milestones; see [current validation status](../validation/status.md).

To add a model, collect its device inventory and document its actual feature routes, then add its identity and verified feature descriptors to `devices.json`. Controls that need device or effects commands should be implemented in their respective adapters; keep those commands out of WPF event handlers. `IAudioBackend.Apply` covers endpoint level/mute. `IMicrophoneEffectsBackend` now supplies read/compare/apply for processing, with a demo adapter and a validated B20 APO adapter. See [protocol evidence and testing](microphone-protocol-and-tests.md).

## 7.1 findings

EPOS documents GSX 300 software-controlled 7.1 surround in its [GSX 300 FAQ](https://www.eposaudio.com/globalassets/__pim/products/gsx-300/8ff41733-ee19-4c3d-b44d-90ae9367aff1_13084_gsx300_faq_en_original.pdf). Its [sound-card comparison](https://www.eposaudio.com/contentassets/a17bd47bb8614ac8a99adb7bb273e3a5/gsx-soundcard-update.pdf) distinguishes the GSX implementation from the older Dolby surround dongles. Treat other products' hardware surround and licensed surround engines as separate implementations until their actual interfaces are established.

Further static inspection of the installed Suite recovered `SoundViewModel.SurroundSound7CommandClick` and `SurroundSound2CommandClick`. The 7.1 method sets nullable `ApoParams.directSoundEnabled` to **true**, while the stereo method sets it to **false**. Both call `pipeServer_SendAgentParamSet` for the playback device, which the earlier inspection maps to service request `13`. The naming must not be interpreted as an inverse bypass flag.

Live Stereo/7.1/Stereo captures now confirm byte 64 = false/true/false; playback EQ uses nine float32 dB values at offsets 76–108. The app writes the shared processor interface directly and signals its existing event, without sending the prepared Suite pipe request. Live mode/EQ readback, restoration and preservation of microphone/reverb configuration pass with the service running. Subsequent user listening passed after the compatible EPOS driver switch/reboot. The separate GSX initializer now has fresh-object control evidence, with fresh-session audible DSP still unvalidated. Replacing the EPOS processor with an independent 7.1 engine additionally needs a system audio integration that obtains multichannel application audio and renders it to the output device.

The initial 2026-10-05 format inspection found GSX 300 playback reporting a two-channel, 48 kHz, 32-bit Windows mix format, while the B20 playback endpoint reported eight channels. After selecting the compatible EPOS driver and rebooting on 2026-10-07, GSX playback exposed eight channels; see [the driver and listening results](../validation/home-validation.md). These are Windows mixer formats, not hardware converter resolution or evidence of a functioning headphone surround effect. [Microsoft GetMixFormat documentation](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getmixformat) explains this distinction.

## Verification

- The regression suite includes the original 20 checks and now adds captured protocol goldens, all legal gate/filter combinations, failure injection, stale state, restoration, and effects profiles. See [testing details](microphone-protocol-and-tests.md).
- A rendered WPF verification exercises microphone apply, profile save/restore, playback feature routing and profile isolation. The screenshot is generated from the actual controls using the demo adapter.
- Live diagnostics discover all four physical EPOS endpoints with USB identities and current mix formats.
- Live control verification lowers B20 and GSX 300 microphone level by two percentage points, reads back the accepted level, and restores their exact previous level and mute state. Both passed. Mute setters were exercised with the original mute value; an audible mute/unmute transition was not used during verification.

B20 gate/filter levels and enable switches, high-pass filtering and nine-band EQ with Flat/Warm/Clear/Custom presets are available through the installed EPOS processor. Effects availability is shown from a successful live read. B20 sidetone level and mute are available through the Windows hardware topology and are included in profiles. See [sidetone implementation and testing](../research/b20-sidetone.md). GSX playback mode/custom EQ/reverb and microphone gate/filter/EQ are available after a successful live read. Its USB sidetone slider and exact raw profile state are supported by a separately guarded HID adapter; high-pass remains unavailable. Reverb enable/amount are validated GSX playback fields; microphone writes preserve them. GSX named device/setup profiles save supported processing, while automatic GSX restore remains unimplemented. A separate [experimental GSX initializer](../research/gsx-initialization.md) now passes fresh-object creation and control/restoration checks with vendor support stopped; fresh audio, cold boot, and managed reconnect remain unvalidated. See [GSX microphone evidence](../research/gsx-microphone-controls.md).

After a failed or incomplete microphone effects read, the editor panel is collapsed and disabled so another device's populated controls cannot appear usable. The reason remains visible, and a successful read restores the editors. This was reproduced on the real B20-to-GSX workflow and rechecked in the built app; see [live audit and interface recommendations](../validation/live-ui-audit-20261006.md).

B20 EQ labels follow the user's Gaming Suite screenshot: 64, 125, 250, 500 Hz, 1, 2, 4, 8 and 16 kHz. The screenshot/mapping is pinned as a fixture and tested against the ordered fields and actual UI labels. On 2026-10-05 the user confirmed noise filter/high-pass operation and audible differences between EQ presets. See [processing evidence](microphone-protocol-and-tests.md) for the scope of manual listening and automated checks.

## Compact control layout

Diagnostics export and device refresh use 32×32 icon buttons in the header. Their background blends with the window, with a subtle border, brighter hover/pressed states and an accent keyboard-focus outline. Tooltips and accessibility names retain the full action labels; click handlers and tab/Enter/Space behavior remain standard buttons.

Buttons, dropdowns, name fields and effect/mute switches use a consistent compact 32-pixel height with 13-pixel labels. Effect and mute states appear in the icon color and red slash, with the control name retained and explicit state in tooltips and accessibility help. Button and text-field padding matches the dropdowns, with aligned rows and accent keyboard focus. Header icons use the same 32-pixel size. The main layout is rendered in `artifacts/icon-state-preview.png`; the setup layout is in `artifacts/consistent-setup-controls-preview.png`. `icon-state-tests.log` confirms 411 regression checks and 99 WPF scenarios, including icon slash, tooltip and accessible state agreement.

Dropdowns share a dark rounded style with a small chevron, an accent focus/open border and a dark popup menu. Selected rows use accent text and a tinted background; mouse/keyboard highlights and dimmed disabled controls remain visible. The same style covers microphone filter/EQ, playback mode and device/setup profile lists, including their existing data templates and selection handlers. Current dropdowns are non-editable.

The styled EQ popup was checked in the real demo window: all four labels fit, mouse selection chose Warm, and Alt+Down / Down / Enter opened the menu and committed Clear with its curve displayed. These interactions use demo adapters. At that UI milestone, the source passed 411 regression checks and 99 WPF scenarios. Evidence: `artifacts/dark-dropdown-preview.png`, `dark-dropdown-ui-smoke.json` and `dark-dropdown-tests.log`.

The microphone page opens the Microphone studio, with blue frequency activity bars and the teal EQ curve overlaid on one plot, sharing frequency positions. The left axis labels activity in dBFS; the right axis labels EQ gain in dB. The combined plot gives activity and EQ 115 pixels of shared height within the existing 170-pixel graph footprint. The gate toggle, slider and percentage sit directly beneath the EQ. Noise filter, its level, high-pass, EQ enable and preset form a wrapping strip; sidetone has its own toggle and level beneath it. Clicking an EQ band reveals the nine adjustment sliders. Opening the studio never starts capture; Live activity remains opt-in and stops on collapse, selection or close.

Custom icons retain standard WPF checkbox and accessibility behavior. Disabled effects show a red diagonal slash and a dimmed icon; their stored level or curve is preserved. Microphone/output mute and sidetone use the reverse checked semantics, showing the red slash when muted. Tooltips and accessibility help describe On, Off, Muted or Unavailable as appropriate. Gate off disables gating only, leaving endpoint mute unchanged. Live/manual application uses the existing guarded adapters and persistence rules.

The header combines selected device, Sound/Microphone navigation, live mode, draft state and endpoint gain/mute. Profiles and device details remain drawers. Hardware metadata, pickup pattern, setup membership shortcuts, readback summaries and monitor/restore details live in the details drawer. Whole-device and page choices remain available through Setup profiles → Devices to include. Switching audio pages resets the detail scroll to the top.

The normal 1040×720 content render verifies that the primary B20 controls fit with live apply on and EQ details collapsed. Narrow windows wrap the effect strip and keep the sliders within its width; expanded details and manual Apply buttons can require scrolling. See `artifacts/merged-microphone-preview.png`. That layout milestone passed 411 regressions and 99 WPF scenarios, including icon states, accessible gate toggling, retained values, mute isolation, manual drafts, saved profile preservation and narrow layout/navigation. The rebuilt live B20 was also inspected at normal size; a manual gate-off click displayed Off and its slash while retaining 50%, with native gate and endpoint mute unchanged (`artifacts/compact-ui-live-draft-readback.json`).
